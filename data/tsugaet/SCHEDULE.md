Сырые ответы сохранены побайтно, включая CRLF и конечные пробелы HTML источника. Их не форматировать: целостность проверяется по manifest; проверка whitespace относится к нашим документам/JSON, а не к исходным ответам.

## Цепочка запросов

[Страница для людей](https://www.nskgortrans.ru/site/rasp) использует `/themes/goodnex/js/raps.min.js` и `https://nskgortrans.ru/components/com_planrasp/helpers/grasp.php`. Авторизация для проверенных ответов не требовалась.

| Шаг | Параметры `grasp.php` | Формат |
|---|---|---|
| Номер | `?q=8` | Строки `номер\|номер\|тип\|код`; тип 1 автобус, 2 троллейбус, 3 трамвай, 8 маршрутка; код соответствует `marsh` (`8`, `0013`, `35`) |
| Направления | `?m=<код>&t=<тип>` | XML `<route id='A\|B' title='Откуда - Куда'/>` |
| Типы дня | `…&r=A` | XML `<schedule id='23' title='ЕЖЕДНЕВНО'/>`; у № 13 — `БУДНИ` (11), `ВЫХОДНОЕ` (5) |
| Остановки | `…&r=A&sch=<id>` | XML `<stop id='<исходный id>\|<порядок>' title='Название'/>` |
| **Полное расписание** | `?tv=mr&m=…&t=…&r=…&sch=…&s=0&v=0` | Несколько заголовков `<h2>` и таблиц: `td_plan_h` — час, `td_plan_m` — минуты в `<div>`, `td_plan_n` — час без отправлений |
| Одна остановка | То же, но `s=<id\|порядок>` | Одна таблица; полезна для контрольного сравнения |
| Интервалы | То же с `v=1` | Начало/конец движения и прогнозируемые интервалы по периодам дня |

`marsh` хранить строкой, не терять ведущие нули. Типы транспорта `listmarsh` (0/1/2/7) отличаются от типов в URL расписания/положений (1/2/3/8). Прямой пример полной страницы: [автобус № 8, A, ежедневно](https://nskgortrans.ru/components/com_planrasp/helpers/grasp.php?tv=mr&m=8&t=1&r=A&sch=23&s=0&v=0).

## Что можно и чего нельзя вывести

- Есть плановые времена по каждой остановке и типу дня. Нет назначения машины на рейс, низкого пола, `graph`, постоянного идентификатора выполнения рейса или явного списка праздничных исключений.
- Равные количества отправлений позволяют исследовать связь по порядку, но не доказывают отсутствие обгонов, укороченных рейсов и пропусков. Проверять монотонность, сутки и последовательность; неоднозначность показывать в отчёте.
- **Хранить время каждого рейса на каждой остановке.** Прежняя гипотеза «постоянный шаблон весь день» опровергнута полным расписанием № 13.
- ID остановок расписания и `trasses` не совпадают ни на одном из трёх проверенных направлений. Нужна явная сверка имён, порядка, соседей и геометрии, включая повторные посещения площадки.
- Дата в шапке HTML не задаёт достоверный срок действия. Подписи календаря интерпретировать явно; неизвестные и сезонные варианты не превращать в «ежедневно». Праздничный календарь требует отдельного источника/решения.
- В шапке есть оговорка о внеплановом проходе машин, следующих из депо/в депо. Такие движения не становятся плановыми пассажирскими рейсами автоматически.

## Объём будущей загрузки

Использовать одну полную страницу на сочетание «маршрут × направление × тип дня». Примерно 300 таких страниц — предварительная оценка, **не итоговое число запросов**: отдельно нужны XML-справочники, каталог и геометрия. Считать фактический объём по обнаруженным данным; первоначальная загрузка и последующее обновление могут отличаться.

Старый расчёт «~9 000 страниц остановок» и предложение брать только конечную с интерполяцией заменены. Рабочая настройка плана — суточная проверка в 03:00 по Новосибирску. Неизменное содержание обновляет только время проверки; при изменении/продлении календаря подготавливается транспортная часть OTP с повторным использованием уличного графа. GPS и низкопольный фильтр обновляются через GTFS-Realtime без сборки графа. Полный обход и регулярный запуск ещё не включены; сначала согласовать фактический объём. Все частоты и порядок реализации — [ROUTING.md](../../docs/ROUTING.md), §7.
