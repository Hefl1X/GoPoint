# Маршруты по расписанию в OpenTripPlanner (шаг 04)

Документ для того, кто продолжает разработку. Он описывает согласованную с владельцем архитектуру, решения, факты о данных и точку, с которой начинать. Состояние на 21.11.2026. Порядок работы, ветки и проверки — в [AGENTS.md](../AGENTS.md) и [ROADMAP.md](ROADMAP.md); команды — в [README](../README.md).

## 1. Зачем

Сейчас транспортную часть маршрута считает собственный поиск на Python (`LiveTransit`: `server/app/services/journey_planner.py` → `server/app/domain/journey_search.py`) **только по машинам, которые сейчас на линии**. OpenTripPlanner строит лишь пешие участки (`otp/build-config.json`: `transitFeeds: []`; `otp/router-config.json`: `updaters: []`; запрос — `server/app/adapters/otp/walk.py`, `directOnly: true, direct: [WALK]`).

Главный дефект: если машина уже проехала остановку посадки, следующего отправления в поиске нет — `server/app/domain/linear.py: stop_calls` отдаёт только остановки впереди машины. Контрольный пример: Цветной проезд → М. «Речной вокзал», 20.11.2026 ≈ 14:10 — «Транспорта сейчас нет», хотя № 8 и маршрутка № 35 идут туда по расписанию.

## 2. Идея (решение владельца)

**Два расписания, маршрут целиком строит OTP.**

1. **Общее расписание** — официальное плановое расписание ЦУГАЭТ (`grasp.php`), переведённое в GTFS.
2. **Низкопольное расписание** — подмножество рейсов общего, у которых по GPS подтверждена низкопольная машина (`ramp = 1`). Строится нашим сервером: каждые 30 с машина из снимка `markers` сопоставляется с рейсом расписания. Расписание ЦУГАЭТ само не говорит, какой рейс низкопольный: машины выходят из депо на рейсы вперемешку.
3. В режиме «Низкопольный транспорт» OTP ищет путь **по низкопольному расписанию**, в режиме «Весь транспорт» — по общему.
4. GPS дополнительно даёт **задержки**: время хода в расписании ЦУГАЭТ одинаково весь день, пробок в нём нет.

### Решения владельца от 21.11.2026

| Вопрос | Решение |
|---|---|
| Движок маршрутов | OTP строит весь маршрут; `LiveTransit` **заменяется полностью**, без переключателя `live/otp`. Перед удалением — сравнение обоих на одних и тех же сохранённых снимках (тест в репозитории, не настройка). |
| Режим по умолчанию | **«Низкопольный транспорт»**. Отменяет решение шага 02 («любой транспорт по умолчанию»). |
| Рейс без подтверждённой низкопольной машины в низкопольном режиме | **Не показывать.** Если подходящих рейсов нет — «Транспорта сейчас нет» и ссылка «Показать любой транспорт». |
| Загрузка расписания с сайта ЦУГАЭТ | **Пока только разовые образцы** (сделаны, см. § 4). Регулярное обновление — только после отдельного согласия владельца. |

## 3. Что такое «поток realtime» и зачем он

OTP читает GTFS только при сборке графа. Всё, что меняется в течение дня, передаётся ему стандартным потоком **GTFS-Realtime** (protobuf): «рейс X опаздывает на 4 мин», «рейс Y отменён». OTP сам забирает поток с нашего сервера (updater `stop-time-updater`, раз в 30 с) и учитывает его при поиске, пересборка не нужна.

Нам он нужен для:
- **задержек** по GPS для обоих расписаний;
- **свежести низкопольного расписания**: рейс становится низкопольным, когда его машина появилась на линии, и перестаёт, если машина сошла.

## 4. Факты о данных (проверено)

Подробности и образцы: [data/tsugaet/SCHEDULE.md](../data/tsugaet/SCHEDULE.md), `data/tsugaet/samples/schedule/` (19 файлов). Источник машин и линий: [data/tsugaet/NSKGORTRANS.md](../data/tsugaet/NSKGORTRANS.md), [docs/DATA_QUALITY.md](DATA_QUALITY.md).

**Расписание (`https://nskgortrans.ru/components/com_planrasp/helpers/grasp.php`):**
- Цепочка: `?q=<номер>` → `?m=<код>&t=<тип>` (направления A/B) → `&r=A` (типы дня: `ЕЖЕДНЕВНО`, `БУДНИ`, `ВЫХОДНОЕ`) → `&sch=<id>` (все остановки направления по порядку) → `?tv=mr&…&s=<id|порядок>&v=0` (HTML: час + минуты отправления с этой остановки).
- Есть: все остановки, все отправления по каждой остановке, первый и последний рейс.
- **Нет:** номера выхода, номера рейса, признака низкого пола.
- **Время хода постоянно весь день**: № 8 A — +2 мин до 2-й остановки, +69 мин до «М. Речной вокзал» у всех 55 рейсов; № 35 A — +78 мин до конечной у всех 97 рейсов. Значит, рейс = отправление с конечной + постоянный шаблон времени хода по остановкам.
- Число отправлений одинаково на всех проверенных остановках направления → рейсы восстанавливаются по порядковому номеру. Укороченные рейсы и заезды в депо на образцах не встречены (проверить на других маршрутах).
- **Id остановок расписания ≠ id площадок `trasses`**, но названия совпадают по порядку (трамвай 13 A: 25 из 25 после `normalize_stop_name` из `server/app/domain/linear.py`; в `trasses` конечная повторяется последней). Привязка — по названию и порядку.
- № 8 A проходит «М. "Речной вокзал"» (31-я из 38 остановок).

**Машины (`markers.php`)** — поля: `title, id_typetr, marsh, graph, direction, lat, lng, time_nav, azimuth, speed, segment_order, ramp, rasp`. `graph` — номер выхода на день; `rasp` — ≈ 5 контрольных остановок со временем, бывает устаревшим и заходит на следующий рейс. Медиана возраста отметки 44 с; `ramp=1` у 61 % машин на линии (у маршруток 3 из 134). Разбор: `server/app/adapters/tsugaet/parse.py`.

**Следствие для низкопольного режима.** Номеров выходов в расписании нет, поэтому подтверждение есть только у рейсов, которые машина с `ramp = 1` уже выполняет (≈ час вперёд). Утром до выезда машин и на поздние рейсы низкопольная выдача будет пустой. Расширение (не обязательно в первой версии): предсказывать следующий рейс той же машины после разворота на конечной.

## 5. Архитектура

```
grasp.php (расписание) ──► ScheduleStore ──► GtfsBuilder ──► gtfs-all.zip ──┐
trasses (площадки, линии) ─┘                                                ├─► OTP: граф (улицы OSM + транспорт)
                                                                            │        ▲ GTFS-Realtime каждые 30 с
markers (GPS, ramp) ─► LiveSnapshotService ─► TripMatcher ─► LowFloorSchedule ─► GtfsRtFeed (наш сервер, внутренний адрес)
                                                │ задержки рейсов ────────────┘
/api/v1/route ─► OtpTransitPlanner (порт) ─► OTP GraphQL planConnection ─► Journey / TransitLeg / WalkLeg (как сейчас)
```

Файлы, названные в заголовках 5.1–5.6, **ещё не существуют** — это предлагаемое размещение нового кода. Существующие модули, на которые они опираются, указаны в тексте.

### 5.1 `ScheduleStore` — `server/app/domain/schedule.py`, `server/app/adapters/tsugaet/schedule.py`
- Модель: маршрут (тип + `marsh`), направление, тип дня, отправления с конечной, шаблон времени хода по остановкам (сдвиг в секундах), привязка каждой остановки расписания к id площадки `trasses`.
- Источник шаблона времени хода — **вопрос владельцу** (§ 8): разово по всем остановкам или по нескольким опорным с интерполяцией по расстоянию вдоль линии (`build_geometry` в `domain/linear.py`). Для первой проверки — опорные остановки из образцов + интерполяция.
- Хранение: JSON-снимок в `data/tsugaet/schedule/` (собирается утилитой из `server/tools/`), загрузка в память при старте.

### 5.2 `GtfsBuilder` — `server/app/domain/gtfs.py`, утилита `server/tools/build_gtfs.py`
- `stops` — площадки `trasses` (их id используют машины и `forecast.php`); `routes` — 104 маршрута, `route_type` по виду (автобус 3, троллейбус 11, трамвай 0, маршрутка 3); `shapes` — линии `trasses` по направлениям; `trips` + `stop_times`; `calendar` из типов дня (`ЕЖЕДНЕВНО` — все дни, `БУДНИ` — пн–пт, `ВЫХОДНОЕ` — сб–вс; праздники не известны).
- Стабильный `trip_id`: `{тип}-{marsh}-{направление}-{id типа дня}-{ЧЧММ отправления с конечной}`. На нём держатся GTFS-Realtime и `/route/check`.
- Маршруты без расписания (если найдутся) — в GTFS не попадают, решение по факту.
- Встраивается в `scripts/build-otp-graph.sh`; `otp/build-config.json` → `transitFeeds`. Граф собирается локально (на сервере 4 ГБ сборка с `-Xmx3g` не поместится).

### 5.3 `TripMatcher` — `server/app/domain/trip_match.py`, сервис `server/app/services/realtime.py`
Каждые 30 с на том же снимке, что карта (`server/app/services/live_snapshot.py`):
1. Положение машины вдоль линии своего направления — `locate` из `domain/linear.py`.
2. Кандидаты — рейсы того же маршрута, направления и типа дня, которые по расписанию сейчас на линии. Задержка кандидата = сейчас − плановое время в точке, где машина.
3. Назначение один-к-одному (жадно по наименьшей |задержке|), границы задержки (например −5…+30 мин — подобрать на данных), устойчивость: прежнее назначение сохраняется, пока не стало явно хуже. На конечной машина назначается на ближайшее отправление.
4. Выход: `trip_id → (машина, задержка, ramp)` и доля сопоставленных машин (служебная метрика; координаты пользователей не пишутся).

Задержка в первой версии распространяется на оставшиеся остановки без изменений.

### 5.4 Низкопольное расписание и его подача в OTP
Рейс низкопольный, если ему назначена машина с `ramp = yes`. Как держать такое расписание в OTP свежим — **выбирается проверкой (этап 1)**:

| Вариант | Как | Что проверить |
|---|---|---|
| А. Отмены через realtime | Отдельный граф (второй экземпляр OTP) со всеми рейсами; поток realtime отменяет (`CANCELED`) все рейсы без подтверждённой низкопольной машины. | Что отменённые рейсы исключаются из поиска; память второго OTP. |
| Б. Пересборка | Раз в несколько минут собирать GTFS только низкопольных рейсов и транспортную часть графа поверх готового уличного, перезагружать второй OTP. | Время пересборки и перезагрузки. |
| В. Один OTP, два фида | В один граф загрузить общий фид и копию рейсов как отдельный фид «низкопольный»; в потоке realtime второго фида неподтверждённые рейсы отменены; в запросе фильтр по фиду/перевозчику. | Есть ли в `planConnection` OTP 2.10 фильтр по фиду или перевозчику; один JVM вместо двух. |

### 5.5 `GtfsRtFeed` — `server/app/api/internal_rt.py`
- Внутренние адреса сервера (Caddy их наружу не отдаёт): `/internal/gtfs-rt/all` (задержки) и `/internal/gtfs-rt/low-floor` (задержки + отмены неподтверждённых, для вариантов А/В). Формат — protobuf, пакет `gtfs-realtime-bindings`.
- `otp/router-config.json` → `updaters: [{"type": "stop-time-updater", "url": "http://server:8000/internal/gtfs-rt/…", "frequency": "30s", "feedId": "…"}]`.
- Машина пропала с линии → рейс **не отменяется** в общем расписании (время по расписанию); в низкопольном — снова неподтверждён.

### 5.6 `OtpTransitPlanner` — порт `TransitPlanner` в `server/app/ports/__init__.py`, адаптер `server/app/adapters/otp/transit.py`
- GraphQL `planConnection` на `/otp/gtfs/v1` (как в `walk.py`), WALK + TRANSIT, несколько вариантов; скорость ходьбы `walk_speed_mps` (1,3 м/с), запасы `board_margin_s` (30 с) и `transfer_margin_s` (60 с) — `server/app/config.py`. Пешие участки по обычному пешеходу (`wheelchair.enabled = false`, решение 14.11).
- Ответ OTP → существующие `Journey`, `TransitLeg`, `WalkLeg` (`server/app/domain/models.py`). Ярлыки «Быстрее всего / Меньше пересадок / Меньше пешком» — перенести логику `_label_variants` из `domain/journey_search.py`. Прямой пеший путь и поле `walk` — как сейчас (`_direct_walk`, `_walk_option` в `services/journey_planner.py`).
- Изменения контракта API (`server/app/api/schemas.py`, затем `openapi_export.py` → `web/src/adapters/api/schema.d.ts`, иначе `check-all.sh` упадёт): у `TransitLeg` добавить `trip_id` и `time_source: realtime | scheduled`, `vehicle_id` сделать необязательным; `/route/check` ищет по `trip_id`.
- Статусы: `no_transit` (в низкопольном режиме — текст про низкопольный транспорт + «Показать любой транспорт»), `transit_unavailable` при недоступном OTP.

### 5.7 Режим по умолчанию
`web/src/shared/settings.tsx`: ключ `gopoint.lowFloorOnly.v3`, по умолчанию `true` (старый `.v2` не переносить); `RouteRequest.low_floor_only = True`, `Meta.low_floor_only_default = True` в `server/app/api/schemas.py`; обновить e2e (`web/e2e/route.spec.ts`, `web/e2e/start.spec.ts`), [DESIGN.md](DESIGN.md).

### 5.8 Что удалить после приёмки
`domain/journey_search.py`, расчётную часть `services/journey_planner.py` (`_trips`, `_vehicle_calls`, `_TransferFix`, `TRANSFER_RETRIES`), `domain/access.py`, их тесты, лишние настройки (`access_*`, `horizon_min`, `transfer_radius_m`). **Остаются**: `domain/linear.py` (нужен `TripMatcher`, карточке машины и прибытиям на остановку), `LiveSnapshotService`, все `/api/v1/live/*`.

## 7. Приёмка

- Docker, 360×640: Цветной проезд → Речной вокзал после ухода автобуса показывает следующее отправление; № 8 и № 35 сравниваются по времени прибытия к Б.
- Низкопольный режим: только подтверждённые рейсы; если их нет — понятное сообщение и «Показать любой транспорт». Поездка с пересадкой, где обе посадки низкопольные.
- Сбой ЦУГАЭТ: маршрут по расписанию, `time_source = scheduled`. Недоступный OTP: `transit_unavailable`.
- Юнит-тесты на фикстурах (как `server/tests/adapters/test_otp_walk.py` — без сети), `bash scripts/check-all.sh`, CI. Замер p95 `/route` и памяти OTP до и после.

## 8. Открытые вопросы владельцу

1. Регулярное обновление расписания. Предложение: раз в сутки (расписание меняется редко) брать только таблицы конечных — ≈ 300 запросов, ≈ 8 мин с паузой 1,5 с. Шаблон времени хода: разово по всем остановкам (≈ 9 000 запросов) или по опорным с интерполяцией.
2. Предсказывать ли следующий рейс низкопольной машины после разворота на конечной (расширяет низкопольную выдачу).

## 9. Правила, которые легко нарушить

- Запросы к ЦУГАЭТ: паузы ≥ 1 с, `User-Agent` из `Settings.user_agent` (`server/app/config.py`). Новые регулярные загрузки — только с согласия владельца.
- Координаты пользователей и поисковые запросы в журналы не пишутся.
- Сторонние адреса и SDK — только в `adapters/` (проверяет `lint-imports`); `domain/` без сети.
- Сетевые тесты — только в `server/tests/network/`, вручную.
